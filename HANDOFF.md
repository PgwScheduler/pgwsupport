# PGW Support Portal — Session Handoff

Recap of everything done so far, for picking up in a fresh Claude Code chat.
See `CLAUDE.md.txt` in this same folder for the original project brief —
that's still the source of truth for business rules (deposit-sheet math,
org hierarchy, roles, ground rules). This file just tracks what's been
*built* against that brief.

## Where things live

- **Frontend app**: `pgw-portal/` — Vite + React + Tailwind, deployed to Vercel
- **Database migrations**: SQL files in the repo root, numbered `01`–`34`, run in order in the Supabase SQL Editor. All 34 have been applied.
- **GitHub repo**: `https://github.com/PgwScheduler/pgwsupport` (branch `main`)
- **Production URL**: `https://pgwsupport.vercel.app` (temporary Vercel URL — custom domain `pgwsupport.com` deliberately not configured yet, per instruction)
- **Local dev**: `cd pgw-portal && npm install && npm run dev` (needs `pgw-portal/.env` with `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` — see `.env.example`)

18. `pgw_speedee_service_categories_19.sql` — **SpeeDee tic-sheet categories** (data only, no schema change). 19. `pgw_store_goals_20.sql` — **Store goals (2026).** `holidays` (5 closures/yr, 2026+2027), `derived_days_open(year,month)` / `annual_days_open(year)` (308 working days in 2026, never hardcoded), `store_annual_goals` (36 stores) + `store_monthly_goals` (cars-per-day + optional day-count override; 324 rows / 27 stores — nine Model-B stores have none), and the derived view `v_store_monthly_gp_target` (annual ÷ working days in year × working days in month). 20. `pgw_tic_sheet_grid_21.sql` — **Tic-sheet category fixes + `first_time_customers`.** Renames in the shared `service_categories`: `kpi_su_ac_heat` → "A/C Refresh", `kpi_su_engine_performance` → "Catalytic Converters" (shared table, so SpeeDee shows the corrected names too — correct, it's the service's real name; SpeeDee's *list* is untouched). Midas renumbered to **30** categories in tens. Adds `daily_kpi.first_time_customers int`.
21. `pgw_daily_kpi_sales_breakdown_22.sql` — adds `daily_kpi.sales_supplies` + `sales_groupon` (Parts/Tire cost already existed). Grid **Sales** = labor+parts+tires+supplies+groupon+discounts; **Gross profit** (goals strip "GP before labor") = Sales − cost_parts − cost_tires.
22. `pgw_daily_kpi_discount_sign_23.sql` — data-only: `sales_discounts` is stored **negative** (a discount reduces Sales). Flips any rows entered as positive (`set sales_discounts = -abs(sales_discounts) where > 0`; idempotent). The Sales panel coerces the entry to negative on save; Sales/GP sum the stored value, so no formula change.
23. `pgw_tech_time_tracker_24.sql` — **Technician Time Tracker.** Nine **slots** per store (`tech_slots`, not nine employees — a slot holds an employee, a placeholder label, or is empty and contributes zero). `tech_daily` (hours/flag/labor per slot per day, store-visible) and the **master/admin-only** `tech_weekly` (weekly `other_pay`) + effective-dated `tech_pay_rates` (`flat_rate` $/flag-hr, `guarantee_rate` $/hr-worked). Pay is **derived, never stored**; weeks run **Sun–Sat**, a month = the five Sun–Sat blocks from the Sunday on/before the 1st. Two SECURITY DEFINER functions return **store-level aggregates only** and are store-callable: `tech_store_month` (labor sales, labor cost, flag/hours, avg tech cost/sold-hr, shop proficiency) and `tech_store_daily` (per-day labor sales for the tic sheet + the **defective** daily allocation for Horizon). The internal `_tech_days` helper emits per-slot pay so it is `REVOKE`d from `PUBLIC`; per-technician pay stays master/admin-only. `tech_pay_rates.flat_rate` is **authoritative** for a tech's flat rate — a trigger (`sync_tech_flat_rate`) mirrors the current effective value into `employee_pay_rates.flat_rate_per_hour`, and the Payroll flat field is read-only for techs. The daily allocation **intentionally over-allocates** (a flag-hours/zero-hours day collects a surplus share; Millwood wk3 allocates $913.15 vs true $896.08) to preserve Horizon continuity — `total_pay` is correct, `daily_allocation` is the defect, both retained. Seed: `pgw_seed_millwood_july_tech.sql` (store #3303). Verified live against `Millwood July 1.xlsm` to the penny (store labor cost $15,640.19, month pay $3,905.20, etc.).
24. `pgw_tic_sheet_totals_25.sql` — **Tic sheet totals, self-correcting goals, zero dollar tickets.** Swaps the unused `daily_kpi.first_time_customers` for **`zero_dollar_tickets`** (daily entry, Summary column F in the source; **no Horizon field** — the upload builder must skip it, the second such field after `local_su_15k_critical_sys`). Zero dollar tickets do **not** reduce `ro_count`, so ROs / capture rate / average estimate per car are untouched. Drops any check constraint mentioning `sales_discounts` so discounts are **signed both ways** (Millwood July: −125.00, −396.53, **+107.00**, netting −1,997.91) — migration 23's blanket `-abs()` flip is **superseded and must not be re-run**. Two new goal tables: **`store_tic_goals`** (per store, `zero_dollar_ticket_pct` default 0.10 — the task called it `store_goals`, renamed to sit beside `store_annual_goals`/`store_monthly_goals`) and **`store_category_goals`** (per store per category, `goal_pct_of_cars` + `average_sale`, seeded from the workbook's company template for every store × its brand's list). Both read via `can_access_location`, write admin/master. Seed: `pgw_seed_millwood_july_kpi.sql` (Millwood #3303, July 2026 — 26 days of ROs / zero-dollar tickets / sales lines / declined / units; `sales_labor` deliberately left 0 because the grid reads labor from `tech_store_daily`).
25. `pgw_bonus_tracker_26.sql` — **Bonus Tracker, four models.** `bonus_plans` (which model a store is on), `bonus_monthly_targets` (days open, car goal, sales goal, GP budget, gold/silver/bronze, **`last_year_gp`**), `bonus_incentive_tiers` (`tire` / `credit_app` / `car_increase`, with `increment_above` on the row that *anchors* the overage rule), `bonus_monthly_inputs` (five-star reviews, phone conversion, Model D's referral GP credit — **nullable on purpose**, null means never entered) and `bonus_flags` (the nine open policy questions, surfaced on screen). **Model D is a fourth structure**, not a variant: SpeeDee Lexington #3308 pays a flat 3% of GP to the store manager with a car-increase-vs-last-year bonus and the Midas referral credit. Because the task demanded *no* thresholds/percentages/scales in code, the model rates live in data too — `bonus_model_rates` (A 7/5/4%, B 3/1.5% manager + 1% assistant, C 4.55/3.25/2.60%, D flat 3%), `bonus_model_splits` (A: GM 65 / Assistant 25 / Advisor 10) and `bonus_policy` ($10 a review, 15-review minimum, $75 penalty, 35-app floor, 40% phone conversion, Model C's $1,000 cap, Model B's 6% improvement). Store tables read via `can_access_location` and write admin/master; the three company-wide tables read to all, write master. Seed `pgw_seed_bonus_2026.sql`: 36 plans (23 A / 9 B / 3 C / 1 D), 432 monthly targets, 232 incentive tiers. **Store names were matched to `store_number` by exact Yearly GP against migration 20's `store_annual_goals`** — all 36 matched uniquely, which is what settles the two non-obvious short names (`Lex` = Lexington Midas #3276, `Wesmark` = #3938). Four handout sheets (Rabon, SD Bush, Broad, PGW North roll-up) have no store here and are not seeded. Note: after running this, PostgREST's schema cache may need `notify pgrst, 'reload schema';` before the new tables are visible to the app.
26. `pgw_bonus_store_reviews_27.sql` — **store managers log their own five-star review count.** Migration 26 had `bonus_monthly_inputs` on admin/master write like the other goal tables, which meant a manager had to phone an admin to record a number only the store can count. Insert/update now go through `can_access_location` (delete stays admin/master). The table is **not** simply opened up: a `before insert or update` trigger (`bonus_inputs_column_guard`) keeps the two money-moving columns admin/master — **`referral_gp_credit`** adds straight into the gross profit the bonus is calculated on, so a Model D store that could type its own number could inflate its own payout, and `phone_conversion_pct` waives the Model A credit penalty. A store's insert gets both forced to their defaults; an update that changes either is refused with `42501`, the same code RLS raises, so the app surfaces it identically. The trigger runs as **invoker** — `current_user_role()` is already SECURITY DEFINER (migration 01), so it needs no elevated rights of its own. Verified live as a store user: logging and editing a review count works, setting the referral credit or phone conversion is refused, and smuggling the referral credit alongside a legitimate review edit rolls the whole statement back (the review change does not sneak through). The client sends only `google_reviews` for a non-admin, so a store save can never trip the guard on a field it did not touch.
27. `pgw_bonus_wesmark_fix_28.sql` — **corrects Wesmark's (#3938 Midas Sumter) corrupt 2026 targets.** `bonus_seed_2026.csv` is column-shifted for this one store: its handout carries three columns the standard Model A sheet does not (a *2025 Sales* column and two *"vs 25"* comparison columns), and the CSV was read positionally, so every value after `sales_goal` landed one column left. `gp_budget` got 2025 Sales, `gold` got the GP Budget, **`silver` got a "vs 25" ratio — $0.26** — and `bronze` got Gold. The effect: any month with more than twenty-six cents of projected GP resolved to Silver and paid 5%, while bronze at $88,214 sat *above* silver and was unreachable; a strong month clearing the real Gold of $88,214 was meanwhile held at Silver by the corrupt $92,857. Wrong in both directions on a store with a $1.1M annual GP budget. All twelve months are restored from the handout's own columns (F/H/J/K) and sum to **1,100,000**, exactly the Yearly GP the sheet states — the check that they are the right columns. **Wesmark's bronze is 85% of budget, not the 80% every other store uses** — that is the handout as written (`K = F * 0.85`), preserved and flagged (`wesmark_bronze_85`). Also adds a `bonus_targets_tier_order` CHECK constraint requiring `gold >= silver >= bronze` where both sides are present, which would have rejected the bad rows at seed time; Model B's null bronze and equal gold/silver in a floored month still pass. Every other store was clean — 312 of the 324 non-Model-B rows are exactly 95/90/80 and the other twelve were Wesmark's.
28. `pgw_tech_slot_management_29.sql` — **Tech Tracker slot management, and the history fix it required.** `tech_daily` referenced only `tech_slot_id`, and `_tech_days` resolved pay rates by joining `tech_slots.employee_id` — the slot's *current* occupant. Reassigning a slot would therefore not merely relabel past days but **re-cost** them at the incoming technician's rates, flowing labor cost → gross profit → the goals strip → the bonus tracker; a reassignment in August would have silently changed July's bonus payout. Fix: **`tech_daily.employee_id`**, stamped at insert by the `tech_daily_stamp_employee` trigger from whoever holds the slot at that moment and never rewritten by a reassignment; `_tech_days` now resolves rates from `td.employee_id`. Existing rows backfilled from current occupancy (valid only because no slot was reassignable before this). Considered and rejected: a slot-assignment history table with effective date ranges — it models the same fact indirectly and makes every read temporal. Reassignment goes through the **`tech_reassign_slot`** RPC so the slot move and the day re-stamp are one transaction; it takes an **effective date** and re-stamps only rows on/after it, returning the count so the UI can preview it before the admin confirms. SECURITY DEFINER, so it re-checks role **and** `can_access_location` itself. Also: partial unique index `tech_slots_one_slot_per_employee (location_id, employee_id) where employee_id is not null`, and `tech_slots` insert/update tightened from `can_access_location` to **admin/master** (a store user could previously rewrite slots through the API even though the UI hid the controls).

29. `pgw_shift_types_30.sql` — **Shift types + month duplication (Employee Schedule).** Company-wide `shift_types` catalog (everyone reads, admin/master writes — 36 stores inventing their own colours makes cross-store review unreadable), seeded with seven: Regular, PTO, UTO, Sick, Training, Holiday, Open/Unassigned. `employee_schedules.shift_type_id` is **nullable** and a null means an ordinary worked shift that renders exactly as before. `counts_toward_hours` drives the weekly totals row; `is_copyable` governs duplication. Two columns beyond the task's DDL: **`export_argb`**, because the screen palette and the Excel palette cannot be the same (screen tokens clear AA on near-black, workbooks are light with black text per index.css), and a `char_length(abbreviation) <= 4` check. Duplication is `schedule_copy_month(location, source, target, mode, commit)` over `_schedule_copy_plan` — **preview and commit read the same plan function, so the summary a user confirms cannot drift from what runs**. Alignment carries each shift's offset in DAYS from the Monday opening the source month's grid onto the Monday opening the target's; that single offset already encodes (week index, weekday), so a Monday lands on a Monday with no special-casing. Verdicts are mutually exclusive: `time_off` / `inactive` / `overflow` / `existing` / `create`. Replace clears the target month first and is **admin/master only**; Fill-empty stays open to anyone `can_access_location` admits, preserving the district/regional edit right from migration 17. The whole copy is one plpgsql body, so a failure rolls back the delete and every insert together.

30. `pgw_open_shifts_31.sql` — **open shifts need no person.** Migration 30 added an "Open / Unassigned" type to a table whose `employee_id` was NOT NULL, so an open shift had to be parked against a real person. Dropping the constraint is one line; **three things break with it and are fixed here.** (1) The copy plan would have skipped every open shift — its verdict reads `when e.id is null or e.active = false then 'inactive'`, and a null `employee_id` makes the left join produce a null `e.id`, so every open shift would have been reported as *"skipped — employee no longer active"* with a null in the names array. The inactive test now applies only when an employee is actually named. (2) Fill-empty would have duplicated them on every run, because the collision test is `x.employee_id = s.employee_id` and `NULL = NULL` is never true — re-running a fill copy is a no-op today and that property would have died silently. Unassigned shifts now collide on `(date, start_time)`. (3) `employee_schedules_uniq` stops constraining unassigned rows, since Postgres treats NULLs as distinct — **left as-is deliberately**, because "we need three people Saturday morning" is expressed as three identical open shifts; duplication-on-copy is handled by (2). Adds `employee_schedules_person_or_type` (`employee_id is not null or shift_type_id is not null`) so a row can never be a blank block with no name and nothing to label it. `employee_id` keeps ON DELETE CASCADE — deleting an employee still removes their shifts rather than turning them into open ones, which is a separate decision.
31. `pgw_payroll_daily_sunday_32.sql` — **Payroll: daily entry, Sunday week, technician hours from the Tech Tracker.** Three changes that only work together. The pay week moves Monday → **Sunday**, matching the tic sheet, tech tracker and bonus math — payroll was the one screen out of step, which put every Sunday in a different week depending on the screen and made payroll-to-sales meaningless. Hours are captured **daily** (`payroll_daily`, unique on `(employee_id, work_date)`, plus `hours_worked_other` keeping the existing "clocked at another store" split rather than widening the key, and `hours_turned` for a uniform grain). **Overtime stays weekly** — one 40-hour threshold on the week's total, never per day. Cutover **2026-08-30**, company-wide, in a single-row `payroll_config` table because a CHECK cannot reference a table, so every rule depending on it is a trigger reading it; nothing is backfilled, since daily detail cannot be recovered from a weekly total. `payroll_config.include_technicians` makes the brief's "one-line change" a one-field change with no deploy. **Both weekly tables flip together** — `timesheet_entries` and `store_week_sales` take `check (dow in (0,1))` plus a shared trigger (Sunday from the cutover, Monday before it); a straight flip to `dow = 0` is impossible while any Monday row exists, and they must move on the same date because `store_week_sales` is the SpeeDee percentage's denominator. Pre-cutover hours are frozen (master keeps an escape hatch); post-cutover weekly hour columns must stay zero or they would be counted by nothing. **One entry per person per day is enforced in both directions** by a trigger on each table — a unique index cannot span two, and neither side silently wins: a collision is refused by name so a human decides. Placeholder slots (`tech_daily.employee_id` null) are exempt. The `tech_daily` guard is an **AFTER** trigger on purpose, because `tech_daily_stamp_employee` (migration 29) is a BEFORE trigger filling `employee_id` and a BEFORE guard would race it on name order. **`payroll_day_hours`** resolves each (person, **day**) to one source, so someone who is a technician for part of a period needs no special case and still gets one weekly overtime threshold. **`payroll_pct_summary` and `flat_flags_for_week` rewritten** to resolve hours through the cutover and to drive off the **roster** rather than `timesheet_entries` — post-cutover an employee can have daily hours and no weekly row, which the old query would have dropped silently. **Salary now keys off `employees.is_store_manager`, not `position = 'manager'`** (one per location, CHECK-constrained to a manager row): the old rule paid every `manager` row a salary and swept assistant managers in with the GM, and BDC's rule — only the GM excluded, assistants stay in — is only coherent if assistants are hourly. **`payroll_to_sales_wtd`** returns window bounds, both wage components, gross sales, the ratio, the technicians flag, `missing_store_manager` and `unattributed_days`; numerator excludes the store manager entirely (not their wages, not their hours, not their day in the window bound) and never adds bonuses or incentives, technicians come in at the Tech Tracker engine's figure with `other_pay` kept, denominator is the tic sheet's own Sales (Groupon excluded per migration 25), and **the window is the intersection** of the days both sides have. Two review catches: `LEAST` ignores nulls, so `least(hours_thru, sales_thru)` would have divided a full week of wages by nothing when one side was empty; and migrations 14/16 both name a CTE column `actual_sales` alongside the OUT parameter of the same name, a latent **42702** ambiguity not copied here.
32. `pgw_dashboard_range_metrics_33.sql` — **Dashboard widgets over an arbitrary date range.** Four functions. **`_tech_pay_range`** (internal, revoked from public) is the range twin of the tech pay engine: it evaluates every WHOLE Sunday–Saturday week a range touches and attributes pay into the range by the share of that week's HOURS falling inside it, so a range covering half a week gets half that week's pay **at full-week rates** and never a half-week overtime calculation. **`tech_store_range`** is its store-callable wrapper, matching `tech_store_month`'s columns exactly — verified identical on Millwood July (labour cost $15,640.19, labour sales $58,582.50, 370.33 flag hours). **`dashboard_range_metrics`** returns the five widgets' figures in one call; **`payroll_to_sales_range`** generalises the Task 8 metric from one week to any span, keeping every rule (store manager excluded entirely, bonuses and incentives never added, technicians at the engine's figure subject to `payroll_config`, both sides over the identical window). **Scoping is done in the database**: `loc` null aggregates across everything `can_access_location()` admits the caller to, which is what lets one dashboard serve a store, district, regional and master with no branching. **Uses the TIC SHEET definition of Sales** (Groupon excluded, migration 25) throughout, per BDC, so the Sales widget, GP% and payroll-to-sales all divide by one number; `groupon` is returned separately so the Summary R35 figure stays one addition away. **Three bugs caught before shipping:** `service_categories.id` is `bigint` not uuid (only locations and employees are uuid-keyed), so the first version failed outright; `sum()` over the `int` columns `credit_apps`/`ro_count`/`units` returns **bigint**, which made `tire_units / days_with_data` **integer division** — 95 tires over 9 days would have silently read 10 rather than 10.56; and because "structure of query does not match function result type" names no column, every returned column is now **cast explicitly** rather than left to inference.
33. `pgw_revoke_internal_helpers_34.sql` — **SECURITY FIX: a store user could read individual technician pay.** `_tech_days` was reachable by any signed-in store user and returned PER-SLOT, PER-DAY `guar_pay`, `commission` and `guar_rate`. `tech_slots` is store-visible, so every row was attributable to a named technician; `guar_rate` handed over their guarantee rate outright and `commission / flag` yields their flat rate. Confirmed live as `teststore@pgwsupport.com` (role `store`, #3303): 83 rows including `guar_rate: 16`. **Root cause:** `revoke all on function ... from public` revokes the PUBLIC pseudo-role, but Supabase separately grants EXECUTE to `authenticated` and `anon`, so the statement was a **no-op** — present since migration 24 and repeated in 29, 30, 31 and 33. The tell was visible all along: `schedule_copy_month` carries the same revoke and the app calls it on every month duplication, so if it had bitten the feature would have been broken from day one. **The fix is deliberately narrow.** `_tech_days` and `_tech_pay_range` are revoked from `anon` and `authenticated`; both are called only by SECURITY DEFINER functions, which run as owner and keep EXECUTE, so no aggregate breaks. **`_schedule_copy_plan` is left reachable on purpose** — `schedule_copy_month` is SECURITY **INVOKER**, so revoking its helper would break Employee Schedule month duplication for every non-superuser; it carries no pay and returns only rows the caller's own RLS already admits. Verified after the fix, as the same store user: the two helpers deny, `tech_store_month`/`_daily`/`_range`, `dashboard_range_metrics` and `payroll_to_sales_range` all still work, and a schedule duplication preview still returns a plan.

## Frontend build order

1. **App shell** — Vite/React/Tailwind scaffold, real Supabase email/password auth (`AuthProvider.jsx`), role-scoped store picker, sidebar/header/breadcrumb (`Shell.jsx`). "Preview as" role switcher removed — role comes from the logged-in profile.
2. **Payroll** (`HoursView.jsx` / `SpeedeeHoursView.jsx`, `usePayroll.js`, `lib/payrollMath.js`) — brand-aware weekly payroll (nav tab renamed "Employee Hours" → "Payroll"). Follows `store.brand`; pay rates/dollars never reach a store user (enforced by RLS, not the UI), stores see percentages only. CSV/print/xlsx export.

## Bugs found and fixed along the way

- **`Card` didn't forward `onClick`** (`ui.jsx`) — broke the Add User modal's click-outside-to-close, since every click inside the modal (including the email field) bubbled to the backdrop and closed it. Fixed by spreading `...rest` props onto `Card`'s div.
- **Vercel env vars never applied to Production** — they were added but no redeploy was triggered (Vite bakes `VITE_*` vars in at build time). Fixed by redeploying after confirming the vars were set.
- **Supabase Site URL still `localhost`** — new-user confirmation emails redirected to a dead `localhost` URL instead of the production app. Needs fixing in Supabase dashboard → Authentication → URL Configuration (Site URL + Redirect URLs should be `https://pgwsupport.vercel.app`). Confirmed the email *confirmation itself* still succeeds server-side even with the bad redirect — affected users can just go straight to the login page and sign in.
- **`@pgwsupport.com` is not a real domain** — it was only ever placeholder text in the login screen's example (`you@pgwsupport.com`). Real company domain is `pgwus.com`. Supabase's signup validation rejects the fake domain; several `*_TEST@pgwsupport.com` accounts in the users list were inserted directly via SQL (bypassing that validation), not through real signups.
- **User Management row state didn't resync after save/revoke** — a row's local role/scope dropdowns kept showing stale values until a full page reload. Fixed with a `useEffect` that resyncs from the server value.

## Known gaps / things not yet built

- No delete-user (only revoke-access, which keeps the Supabase Auth login intact but strips all access) — a true delete would need a `service_role` key in a serverless function, deliberately avoided so far.
- No password-change / forgot-password UI for end users yet.
- Custom domain (`pgwsupport.com`) not configured on Vercel — deliberate, per instruction to test on the temporary URL first.
- Google review counting is **on hold pending a decision** — the manual entry field from Task 6 stays; no automatic counting and no widget were built, deliberately.
- The brief's "Upgrade once live" export items — cross-store/date-range exports for admins/payroll, real `.xlsx` output — not started.
- **No store manager is flagged at any store yet**, because no real rosters exist (9 employees across 3 of 36 stores). The payroll-to-sales exclusion therefore ships *inert*. The risk is not the migration — it is whoever enters 36 rosters later typing GMs as `position = 'manager'` and leaving `is_store_manager` false, which would put a salaried GM's pay in every store's numerator. The widget's `missing_store_manager` warning exists to catch exactly that, and it is the thing to watch when rosters are built.
- **Payroll-to-sales covers post-cutover weeks only.** It reads daily rows; a pre-cutover week holds one weekly total per person and a week-to-date figure cannot be derived from it. This is a property of the metric, not a gap to close.
- SpeeDee payroll remains **entirely unexercised** — no SpeeDee store has a single employee. Its day columns were built alongside Midas's because `payroll_daily` is brand-agnostic, but nothing has run against them.
- Local dev sessions in the Browser pane tool have repeatedly lost `localStorage` (and thus the login session) between turns — not an app bug, just a quirk of the sandboxed browser tool; re-login is needed each time this happens.
