# PGW Support Portal — Session Handoff

Recap of everything done so far, for picking up in a fresh Claude Code chat.
See `CLAUDE.md.txt` in this same folder for the original project brief —
that's still the source of truth for business rules (deposit-sheet math,
org hierarchy, roles, ground rules). This file just tracks what's been
*built* against that brief.

## Where things live

- **Frontend app**: `pgw-portal/` — Vite + React + Tailwind, deployed to Vercel
- **Database migrations**: SQL files in the repo root, numbered `01`–`29`, run in order in the Supabase SQL Editor. All 29 have been applied.
- **GitHub repo**: `https://github.com/PgwScheduler/pgwsupport` (branch `main`)
- **Production URL**: `https://pgwsupport.vercel.app` (temporary Vercel URL — custom domain `pgwsupport.com` deliberately not configured yet, per instruction)
- **Local dev**: `cd pgw-portal && npm install && npm run dev` (needs `pgw-portal/.env` with `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` — see `.env.example`)

12. `pgw_profiles_email_13.sql` — mirrors `auth.users.email` onto `profiles.email` (via the signup trigger + a backfill), so the User Management screen can list users without needing Supabase's admin API
13. `pgw_employee_hours_payroll_rebuild_14.sql` — replaced the weekly `employee_hours` grid with the full payroll model: `employees`, `timesheet_entries` (store-visible) and the pay tables `employee_pay_rates` + `timesheet_pay` (**master/admin-only RLS — a store SELECT returns zero rows**). Pay is derived on read; stores see only percentages via the `payroll_pct_summary()` SECURITY DEFINER function. `employee_hours` dropped.
14. `pgw_flat_flags_for_store_15.sql` — flat-rate-vs-hourly flag helper used by the payroll percentage view.
15. `pgw_speedee_brand_16.sql` — made payroll brand-aware. Added **`locations.brand`** (`'midas'`/`'speedee'`, default midas) and set stores **3009/3025/3029/3308 → speedee**; split `timesheet_entries` into shared core + `timesheet_midas`/`timesheet_speedee`; added `brand_settings`, `role_sales_rates`, `store_week_sales`, and the `payroll_speedee_summary()` RPC.
16. `pgw_employee_schedules_17.sql` — `employee_schedules` (per-store shift calendar, timezone-naive `date`+`time`, no overnight shifts). Access via `can_access_location()`; references only the `employees` roster, never pay data.
17. `pgw_daily_tic_sheet_18.sql` — **Daily Tic Sheet.** Reference tables `service_categories` + `brand_service_categories` (seeded with the 29 Midas categories, `display_order` 10..290; `horizon_key` values are the external system's exact field names). Data tables `daily_kpi` (one row per store per `business_date`) + `daily_service_units`. Uses `location_id uuid → locations(id)` (there is no bigint `stores` table); does **not** re-add `brand` (already present from migration 16). RLS mirrors the cash-drawer tables — read/insert/update via `can_access_location(location_id)`, delete master-only, child units resolved through the parent row; the two reference tables are readable by all authenticated users and **master-only** to write.
18. `pgw_speedee_service_categories_19.sql` — **SpeeDee tic-sheet categories** (data only, no schema change). Adds two new `service_categories` (`kpi_su_axels_shafts` "Axels & Shafts", `kpi_su_tire_rotation` "Tire Rotation") and 31 `brand_service_categories` rows for `brand='speedee'` (`display_order` 10..310, a different roughly-alphabetical order with the two new lines slotted in, not appended). Leaves the 29 Midas rows untouched; the two new categories map to SpeeDee only. The entry screen picks these up with no code change (it filters by the location's brand).
19. `pgw_store_goals_20.sql` — **Store goals (2026).** `holidays` (5 closures/yr, 2026+2027), `derived_days_open(year,month)` / `annual_days_open(year)` (308 working days in 2026, never hardcoded), `store_annual_goals` (36 stores) + `store_monthly_goals` (cars-per-day + optional day-count override; 324 rows / 27 stores — nine Model-B stores have none), and the derived view `v_store_monthly_gp_target` (annual ÷ working days in year × working days in month). Built from the supplied `step2_goals_seed.sql` unchanged in values; **added on top**: RLS (goals read via `can_access_location`, write admin/master; `holidays` read-all, master-write), `security_invoker = true` on the view so a store user reading it is scoped by the base-table RLS (else it would leak every store's targets), and idempotency guards.
20. `pgw_tic_sheet_grid_21.sql` — **Tic-sheet category fixes + `first_time_customers`.** Renames in the shared `service_categories`: `kpi_su_ac_heat` → "A/C Refresh", `kpi_su_engine_performance` → "Catalytic Converters" (shared table, so SpeeDee shows the corrected names too — correct, it's the service's real name; SpeeDee's *list* is untouched). New category `local_su_15k_critical_sys` ("15K Critical Sys Treatment"), Midas only, slotted after Fuel Injection Flush — the `local_` prefix marks a key with **no Horizon field**, so downstream upload code must not assume every key maps to Horizon. Midas renumbered to **30** categories in tens. Adds `daily_kpi.first_time_customers int`.
21. `pgw_daily_kpi_sales_breakdown_22.sql` — adds `daily_kpi.sales_supplies` + `sales_groupon` (Parts/Tire cost already existed). Grid **Sales** = labor+parts+tires+supplies+groupon+discounts; **Gross profit** (goals strip "GP before labor") = Sales − cost_parts − cost_tires.
22. `pgw_daily_kpi_discount_sign_23.sql` — data-only: `sales_discounts` is stored **negative** (a discount reduces Sales). Flips any rows entered as positive (`set sales_discounts = -abs(sales_discounts) where > 0`; idempotent). The Sales panel coerces the entry to negative on save; Sales/GP sum the stored value, so no formula change.
23. `pgw_tech_time_tracker_24.sql` — **Technician Time Tracker.** Nine **slots** per store (`tech_slots`, not nine employees — a slot holds an employee, a placeholder label, or is empty and contributes zero). `tech_daily` (hours/flag/labor per slot per day, store-visible) and the **master/admin-only** `tech_weekly` (weekly `other_pay`) + effective-dated `tech_pay_rates` (`flat_rate` $/flag-hr, `guarantee_rate` $/hr-worked). Pay is **derived, never stored**; weeks run **Sun–Sat**, a month = the five Sun–Sat blocks from the Sunday on/before the 1st. Two SECURITY DEFINER functions return **store-level aggregates only** and are store-callable: `tech_store_month` (labor sales, labor cost, flag/hours, avg tech cost/sold-hr, shop proficiency) and `tech_store_daily` (per-day labor sales for the tic sheet + the **defective** daily allocation for Horizon). The internal `_tech_days` helper emits per-slot pay so it is `REVOKE`d from `PUBLIC`; per-technician pay stays master/admin-only. `tech_pay_rates.flat_rate` is **authoritative** for a tech's flat rate — a trigger (`sync_tech_flat_rate`) mirrors the current effective value into `employee_pay_rates.flat_rate_per_hour`, and the Payroll flat field is read-only for techs. The daily allocation **intentionally over-allocates** (a flag-hours/zero-hours day collects a surplus share; Millwood wk3 allocates $913.15 vs true $896.08) to preserve Horizon continuity — `total_pay` is correct, `daily_allocation` is the defect, both retained. Seed: `pgw_seed_millwood_july_tech.sql` (store #3303). Verified live against `Millwood July 1.xlsm` to the penny (store labor cost $15,640.19, month pay $3,905.20, etc.).
24. `pgw_tic_sheet_totals_25.sql` — **Tic sheet totals, self-correcting goals, zero dollar tickets.** Swaps the unused `daily_kpi.first_time_customers` for **`zero_dollar_tickets`** (daily entry, Summary column F in the source; **no Horizon field** — the upload builder must skip it, the second such field after `local_su_15k_critical_sys`). Zero dollar tickets do **not** reduce `ro_count`, so ROs / capture rate / average estimate per car are untouched. Drops any check constraint mentioning `sales_discounts` so discounts are **signed both ways** (Millwood July: −125.00, −396.53, **+107.00**, netting −1,997.91) — migration 23's blanket `-abs()` flip is **superseded and must not be re-run**. Two new goal tables: **`store_tic_goals`** (per store, `zero_dollar_ticket_pct` default 0.10 — the task called it `store_goals`, renamed to sit beside `store_annual_goals`/`store_monthly_goals`) and **`store_category_goals`** (per store per category, `goal_pct_of_cars` + `average_sale`, seeded from the workbook's company template for every store × its brand's list). Both read via `can_access_location`, write admin/master. Seed: `pgw_seed_millwood_july_kpi.sql` (Millwood #3303, July 2026 — 26 days of ROs / zero-dollar tickets / sales lines / declined / units; `sales_labor` deliberately left 0 because the grid reads labor from `tech_store_daily`).
25. `pgw_bonus_tracker_26.sql` — **Bonus Tracker, four models.** `bonus_plans` (which model a store is on), `bonus_monthly_targets` (days open, car goal, sales goal, GP budget, gold/silver/bronze, **`last_year_gp`**), `bonus_incentive_tiers` (`tire` / `credit_app` / `car_increase`, with `increment_above` on the row that *anchors* the overage rule), `bonus_monthly_inputs` (five-star reviews, phone conversion, Model D's referral GP credit — **nullable on purpose**, null means never entered) and `bonus_flags` (the nine open policy questions, surfaced on screen). **Model D is a fourth structure**, not a variant: SpeeDee Lexington #3308 pays a flat 3% of GP to the store manager with a car-increase-vs-last-year bonus and the Midas referral credit. Because the task demanded *no* thresholds/percentages/scales in code, the model rates live in data too — `bonus_model_rates` (A 7/5/4%, B 3/1.5% manager + 1% assistant, C 4.55/3.25/2.60%, D flat 3%), `bonus_model_splits` (A: GM 65 / Assistant 25 / Advisor 10) and `bonus_policy` ($10 a review, 15-review minimum, $75 penalty, 35-app floor, 40% phone conversion, Model C's $1,000 cap, Model B's 6% improvement). Store tables read via `can_access_location` and write admin/master; the three company-wide tables read to all, write master. Seed `pgw_seed_bonus_2026.sql`: 36 plans (23 A / 9 B / 3 C / 1 D), 432 monthly targets, 232 incentive tiers. **Store names were matched to `store_number` by exact Yearly GP against migration 20's `store_annual_goals`** — all 36 matched uniquely, which is what settles the two non-obvious short names (`Lex` = Lexington Midas #3276, `Wesmark` = #3938). Four handout sheets (Rabon, SD Bush, Broad, PGW North roll-up) have no store here and are not seeded. Note: after running this, PostgREST's schema cache may need `notify pgrst, 'reload schema';` before the new tables are visible to the app.
26. `pgw_bonus_store_reviews_27.sql` — **store managers log their own five-star review count.** Migration 26 had `bonus_monthly_inputs` on admin/master write like the other goal tables, which meant a manager had to phone an admin to record a number only the store can count. Insert/update now go through `can_access_location` (delete stays admin/master). The table is **not** simply opened up: a `before insert or update` trigger (`bonus_inputs_column_guard`) keeps the two money-moving columns admin/master — **`referral_gp_credit`** adds straight into the gross profit the bonus is calculated on, so a Model D store that could type its own number could inflate its own payout, and `phone_conversion_pct` waives the Model A credit penalty. A store's insert gets both forced to their defaults; an update that changes either is refused with `42501`, the same code RLS raises, so the app surfaces it identically. The trigger runs as **invoker** — `current_user_role()` is already SECURITY DEFINER (migration 01), so it needs no elevated rights of its own. Verified live as a store user: logging and editing a review count works, setting the referral credit or phone conversion is refused, and smuggling the referral credit alongside a legitimate review edit rolls the whole statement back (the review change does not sneak through). The client sends only `google_reviews` for a non-admin, so a store save can never trip the guard on a field it did not touch.
27. `pgw_bonus_wesmark_fix_28.sql` — **corrects Wesmark's (#3938 Midas Sumter) corrupt 2026 targets.** `bonus_seed_2026.csv` is column-shifted for this one store: its handout carries three columns the standard Model A sheet does not (a *2025 Sales* column and two *"vs 25"* comparison columns), and the CSV was read positionally, so every value after `sales_goal` landed one column left. `gp_budget` got 2025 Sales, `gold` got the GP Budget, **`silver` got a "vs 25" ratio — $0.26** — and `bronze` got Gold. The effect: any month with more than twenty-six cents of projected GP resolved to Silver and paid 5%, while bronze at $88,214 sat *above* silver and was unreachable; a strong month clearing the real Gold of $88,214 was meanwhile held at Silver by the corrupt $92,857. Wrong in both directions on a store with a $1.1M annual GP budget. All twelve months are restored from the handout's own columns (F/H/J/K) and sum to **1,100,000**, exactly the Yearly GP the sheet states — the check that they are the right columns. **Wesmark's bronze is 85% of budget, not the 80% every other store uses** — that is the handout as written (`K = F * 0.85`), preserved and flagged (`wesmark_bronze_85`). Also adds a `bonus_targets_tier_order` CHECK constraint requiring `gold >= silver >= bronze` where both sides are present, which would have rejected the bad rows at seed time; Model B's null bronze and equal gold/silver in a floored month still pass. Every other store was clean — 312 of the 324 non-Model-B rows are exactly 95/90/80 and the other twelve were Wesmark's.
28. `pgw_tech_slot_management_29.sql` — **Tech Tracker slot management, and the history fix it required.** `tech_daily` referenced only `tech_slot_id`, and `_tech_days` resolved pay rates by joining `tech_slots.employee_id` — the slot's *current* occupant. Reassigning a slot would therefore not merely relabel past days but **re-cost** them at the incoming technician's rates, flowing labor cost → gross profit → the goals strip → the bonus tracker; a reassignment in August would have silently changed July's bonus payout. Fix: **`tech_daily.employee_id`**, stamped at insert by the `tech_daily_stamp_employee` trigger from whoever holds the slot at that moment and never rewritten by a reassignment; `_tech_days` now resolves rates from `td.employee_id`. Existing rows backfilled from current occupancy (valid only because no slot was reassignable before this). Considered and rejected: a slot-assignment history table with effective date ranges — it models the same fact indirectly and makes every read temporal. Reassignment goes through the **`tech_reassign_slot`** RPC so the slot move and the day re-stamp are one transaction; it takes an **effective date** and re-stamps only rows on/after it, returning the count so the UI can preview it before the admin confirms. SECURITY DEFINER, so it re-checks role **and** `can_access_location` itself. Also: partial unique index `tech_slots_one_slot_per_employee (location_id, employee_id) where employee_id is not null`, and `tech_slots` insert/update tightened from `can_access_location` to **admin/master** (a store user could previously rewrite slots through the API even though the UI hid the controls).

9. **Daily Tic Sheet** (`TicSheetView.jsx`, `useMonthlyTicSheet.js`, `useMonthlyGoals.js`, `lib/workdays.js`) — Midas store manager's monthly entry, laid out as the **month grid** the managers already use (reworked from the original one-day form; the old `useDailyKpi.js` was removed). One row per day of the selected month (Sundays, holidays, and future days are visible but muted / not editable), one column per service category in `display_order` (30 for Midas, vertical headers so they fit), then the day-summary columns. Frozen day column + header band (the **Actual % of Cars** band = MTD units ÷ MTD ROs; per-category **Goal %/Goal Units** rows are hidden until penetration goals exist); horizontal scroll for 30+ columns; **Totals** row (month-to-date sums) at the bottom. Cells edit in place with **per-cell autosave** (Tab across a day, Enter down a column) — no Save/Submit button (`submitted_at` stays in the DB, unused by the grid). Day-summary columns: Repair Orders, First Time Customers, **Sales** (computed = labor+parts+tires+supplies+groupon+discounts, where `sales_discounts` is stored **negative** so it reduces Sales; opens a per-day breakdown panel with those 6 revenue lines + Parts Cost/Tire Cost, showing Sales total and Gross profit), Declined Sales, CC Apps, Credit $, and three read-only computed columns — Total Potential (Sales+Declined), Ave Estimate/Car (Total Potential÷ROs, blank when ROs=0), Sales Capture Rate (Sales÷Total Potential, blank when 0). The **goals summary strip** still sits above the grid; its "GP before labor" = Sales − Parts Cost − Tire Cost. Scope is data entry only: no bonuses, technician entry, pay math, or uploads. Verified live: 30 columns correctly named/ordered (15K Critical Sys between F/I Flush and Gear Box Flush), 31 rows with muted Sundays/July 4, autosave round-trip, totals, Actual %, the computed columns, zero-RO blanks, and the 8-field breakdown panel (Sales/GP math). Cross-store isolation rides on the unchanged `daily_kpi` RLS proven earlier (403 `42501`).
10. **Deployment** — GitHub repo created, pushed, Vercel project imported with Root Directory set to `pgw-portal`, env vars configured, auto-deploys on push to `main`.
11. **Tech Tracker** (`TechTrackerView.jsx`, `useTechTracker.js`, `lib/techPayMath.js`, `lib/grossProfit.js`) — new nav tab. Per-technician monthly view: five Sun–Sat week blocks, columns `Work Day # | Day | Hrs Worked | Flag Hours | Labor Sales | ELR | Guar Pay | Commission | O/T | Total Pay`, weekly + month totals, the "on overtime in N more worked hours" countdown. Managers type only Hrs/Flag/Labor (autosave on blur, Enter moves down); **pay columns render only for master/admin** and are enforced by RLS (store users have no rates, so no endpoint returns pay). A store-level **technician summary** table (Summary!P25:T34 — Proficiency, ELR, and, master-only, Labor GP % + Cost/Hour) and a master **effective-dated rate editor**. `techPayMath.js` mirrors the SQL pay engine exactly (incl. the deliberate daily-allocation defect, commented); `grossProfit.js` completes portal GP. Both have `*.test.mjs` (run with `node`, 35 assertions). **Part 4 wiring:** the tic sheet's **Labor Sales is now read-only** (locked, sourced from `tech_store_daily`) — `useMonthlyTicSheet` exposes `laborSalesByDate` and every sales figure adds it to the remaining `daily_kpi` lines; the goals strip now shows **full gross profit** (labor cost deducted via `computeGrossProfit`), replacing the old "GP before labor" described in feature 9. Payroll's flat-rate field is read-only for techs (mirrors `tech_pay_rates`). Verified live on Millwood #3303 July 2026: Phillip Brayboy wk1 $547.20 / wk2 $906.40 / wk3 $896.08 (alloc $913.15) / month $3,905.20, store labor cost $15,640.19, avg cost/sold-hr $42.23, shop proficiency 49.9%, tic-sheet Labor Sales $3,887.98 (Jul 1) locked. Note: store ELR reads $158.19 until `daily_kpi` groupon is entered (the $156.92 target is groupon-blended, `(labor+0.5·groupon)/flag`).
12. **Tic sheet totals + self-correcting goals** (`lib/ticSheetMath.js` + `ticSheetMath.test.mjs`, rewritten `TicSheetView.jsx`, extended `useMonthlyTicSheet.js`, `moneyCell()` in `lib/format.js`) — the month grid now matches `Maint Tic Sheet` end to end. Day rows are grouped into **Sunday–Saturday week blocks**, each followed by three rows: **Weekly Totals** (column sums; the two ratio columns *recompute* — Ave Estimate/Car = weekly Potential ÷ weekly ROs, Capture Rate = weekly Sales ÷ weekly Potential), **New Goal**, and **Weekly % of Cars** (weekly units ÷ weekly ROs). At the bottom: **Monthly Total** (the sum of the Weekly Totals rows, ratios recomputed) and **PACE** = MTD ÷ (days elapsed ÷ days open), with the source's legend line under the grid. *New Goal* is cumulative remaining units — `monthly_goal = goal % × projected ROs`, then each week subtracts its own total from the previous remainder, so slipping in week 1 raises week 2's target; **negatives display with the minus sign** (Millwood finished July at −43.6 tires / −36.9 LOF Prem) and are never clamped. `projected_repair_orders = MTD ROs ÷ days elapsed × days open`, where *days elapsed* counts **entered** days, not calendar days. The **header band** (frozen with the day column) is five rows: Goals % of Cars and Average Sale (both entered — inline-editable for admin/master, read-only for stores), Actual % of Cars, Actual Sales (units × average sale) and Goal Units. **Zero Dollar Tickets** replaces First Time Customers as a day-summary column with MTD count, % of ROs in the band (flagged red over the store's goal — Millwood 15.9% vs 10%) and a PACE figure. Discounts are entered **signed** (the panel no longer coerces to negative). Money cells render through `moneyCell()`, the JS mirror of `CURRENCY_FMT` (`$#,##0.00;-$#,##0.00;"-"??`), so screen and Excel export agree. **Two source bugs deliberately not replicated:** A/C Refresh / Catalytic Converters / 15K Critical Sys point their goal formula at an empty cell in the spreadsheet and read zero forever — here every category uses the same projected-RO source; and the sheet hardcodes five week blocks, which silently drops the last two days of a 31-day month starting Saturday (August 2026) — `monthWeekBlocks()` emits as many blocks as the month needs. **Sales now excludes Groupon**, matching the source's Sales column (`Summary G+H+J+L+N`, no M) — this changes the formula recorded under migration 22; Groupon is still entered in the breakdown panel and still feeds gross profit, where the source splits it 50/50 across labor and parts. `ticSheetMath.test.mjs` runs the whole Millwood July month offline (`node src/lib/ticSheetMath.test.mjs`, 62 assertions).
13. **Bonus Tracker** (`components/BonusView.jsx`, `hooks/useBonusTracker.js`, `lib/bonusMath.js` + `bonusMath.test.mjs`) — new nav tab, all four models. Every model measures **projected month-end gross profit** — `(MTD GP ÷ days elapsed) × days open`, where *days elapsed* counts entered days — so it answers "what will I earn if the rest of the month looks like this" rather than being a scoreboard; both figures are shown side by side and converge at close. GP is the same `computeGrossProfit()` the tic sheet's goals strip uses, so **technician labor cost is already deducted** — before the tech tracker existed this ran ~20% high, enough to move Millwood two full tiers. `bonusMath.js` contains **no number at all**: rates, splits, thresholds, scales and policy scalars are all arguments loaded from migration 26. **Two standing decisions, both flagged on screen:** (1) penalties are calculated and displayed but **never deducted** — the pool is shown gross with "if it were applied the total would be $X" beside it, because Model A's waiver turns on phone conversion, which nothing tracks; (2) the Millwood workbook zeroes the credit-app kicker whenever projected GP clears Gold, so its best months lose it — that is a defect, and the kicker is paid at Gold here. Unpaid lines say **why**: *locked* (a GP gate is unmet), *not reached* (the measure missed a rung), *not entered* (nobody has typed it) — an un-entered figure is never rendered as $0.00. Every screen carries the estimate disclaimer. Conflict flags are location-scoped (Millwood shows 8, #3308 shows 9 — the extra being its own Model C-vs-D question). Verified live on Millwood July 2026: Bronze, pool $4,579.04 = $3,329.04 base + $1,250 tire, split $2,976.38 / $1,144.76 / $457.90; $2,100 penalty shown not applied; pushing GP past Gold gives $9,050 with tire and credit intact. Item 9 proved end to end by changing one technician day's hours: labor cost −$34.00 → GP +$34.00 → pool +$1.36 → GM +$0.88, then restored exactly. ## Bugs found and fixed along the way

- **`Card` didn't forward `onClick`** (`ui.jsx`) — broke the Add User modal's click-outside-to-close, since every click inside the modal (including the email field) bubbled to the backdrop and closed it. Fixed by spreading `...rest` props onto `Card`'s div.
- **Vercel env vars never applied to Production** — they were added but no redeploy was triggered (Vite bakes `VITE_*` vars in at build time). Fixed by redeploying after confirming the vars were set.
- **Supabase Site URL still `localhost`** — new-user confirmation emails redirected to a dead `localhost` URL instead of the production app. Needs fixing in Supabase dashboard → Authentication → URL Configuration (Site URL + Redirect URLs should be `https://pgwsupport.vercel.app`). Confirmed the email *confirmation itself* still succeeds server-side even with the bad redirect — affected users can just go straight to the login page and sign in.
- **`@pgwsupport.com` is not a real domain** — it was only ever placeholder text in the login screen's example (`you@pgwsupport.com`). Real company domain is `pgwus.com`. Supabase's signup validation rejects the fake domain; several `*_TEST@pgwsupport.com` accounts in the users list were inserted directly via SQL (bypassing that validation), not through real signups.
- **User Management row state didn't resync after save/revoke** — a row's local role/scope dropdowns kept showing stale values until a full page reload. Fixed with a `useEffect` that resyncs from the server value.

- Custom domain (`pgwsupport.com`) not configured on Vercel — deliberate, per instruction to test on the temporary URL first.
